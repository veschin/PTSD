PTSD

AI writes code on vibes.

This tool makes it think first.

go install github.com/veschin/ptsd/cmd/ptsd@latest

Go 1.25+ -- single binary -- zero dependencies

Quick Start ↓

AI agents jump straight to code. They skip requirements, write tests as afterthought, hallucinate edge cases. The result works -- until it doesn't.

PTSD enforces a pipeline: think, then prove, then build. Every feature earns its way into the codebase.

01

Requirements

Define what you're building before anyone writes a line of code. Acceptance criteria, edge cases, non-goals. The AI reads this as its contract -- not a suggestion, a constraint.

<!-- feature:auth -->
## Authentication

Users log in with email and password.

Acceptance criteria:
- Valid credentials -> JWT token
- Invalid credentials -> 401 error
- Locked account -> 403 with reason

Non-goals: social login, 2FA
02

Golden Data

Prepare real examples of what the code will handle. Not test_user or foo@bar.com -- actual records, actual edge cases. This grounds everything that follows in reality.

Optional. Only required in the full pipeline profile.

# .ptsd/seeds/auth/users.json
[
  {"email": "ada@example.com", "role": "admin", "status": "active"},
  {"email": "locked@test.co", "status": "locked", "reason": "brute force"}
]
03

Behavior Scenarios

Given/When/Then specifications. Each scenario is a concrete claim: given this input, when this happens, then this is the result. Machines can verify claims. They can't verify vibes.

Optional for lite profile. Write tests directly from PRD.

@feature:auth
Feature: Authentication

  Scenario: Successful login
    Given user "ada@example.com" exists and is active
    When she submits valid credentials
    Then a JWT token is returned

  Scenario: Locked account
    Given user "locked@test.co" is locked
    When login is attempted
    Then 403 is returned with reason
04

Tests Before Code

Write tests that fail. Red lights. They define what done means before implementation starts. No mocks for internal code -- real files, real I/O, real behavior.

// auth_test.go -- tests written BEFORE implementation
func TestLogin_ValidCredentials(t *testing.T) {
    user := seedUser(t, "ada@example.com", "active")

    token, err := auth.Login(user.Email, user.Password)

    assert(t, err == nil)
    assert(t, token != "")
}

func TestLogin_LockedAccount(t *testing.T) {
    user := seedUser(t, "locked@test.co", "locked")

    _, err := auth.Login(user.Email, user.Password)

    assert(t, errors.Is(err, auth.ErrLocked))
}
05

Implementation

Now write code. Only to make failing tests pass. Nothing speculative, nothing extra. The pipeline already ensured you know what to build and how to prove it works.

// Only code that makes tests pass. Nothing extra.
func Login(email, password string) (string, error) {
    user, err := store.FindByEmail(email)
    if err != nil {
        return "", ErrInvalidCredentials
    }
    if user.Status == "locked" {
        return "", ErrLocked
    }
    if !verify(password, user.HashedPassword) {
        return "", ErrInvalidCredentials
    }
    return generateJWT(user), nil
}

Not every feature needs five stages

Choose a pipeline profile per feature. Complex data-heavy work gets the full treatment. Simple utilities skip what they don't need.

full
PRD → Seed → BDD → Tests → Impl
standard
PRD → Seed → BDD → Tests → Impl
lite
PRD → Seed → BDD → Tests → Impl
# Assign a profile when adding a feature ptsd feature add auth "Authentication" --pipeline full ptsd feature add config "App Config" --pipeline lite # Change later if needs evolve ptsd feature pipeline auth standard

How enforcement works

PTSD doesn't rely on the AI following instructions voluntarily. Hooks intercept every file write and every commit.

Session Start
Context injected once. AI sees current stage and next action per feature.
File Write
Gate checks stage. Wrong stage? Write is blocked before it happens.
After Write
Stage advances automatically. No manual tracking needed.
Commit
Validate runs. Broken pipeline, bad format -- commit is blocked.

Works with your tool

Run ptsd init -- it detects your AI tool and generates the right integration. Switch tools later with ptsd init --tool <name>.

Claude Code
.claude/settings.json   -- 3 hooks
.claude/hooks/*.sh      -- gate, track, context
.claude/skills/         -- 13 auto-discovered skills
CLAUDE.md               -- pipeline instructions

Full enforcement. Every write checked, every stage tracked.

OpenCode
.opencode/plugins/ptsd.ts  -- gate + track hooks
.opencode/commands/*.md    -- 13 commands
AGENTS.md                  -- pipeline instructions

Plugin-based enforcement. Same pipeline, different tool.

Generic
AGENTS.md               -- pipeline instructions
.git/hooks/pre-commit   -- validates on commit
.git/hooks/commit-msg   -- validates format

Git hooks enforce at commit. AI follows instructions voluntarily.

13 specialized instructions

Each pipeline stage has a skill -- a focused instruction set that tells the AI exactly what to produce, what to check, and what mistakes to avoid. The AI doesn't guess how to write BDD scenarios -- it follows a concrete checklist.

--- name: write-tests description: Write tests from BDD scenarios --- 1. One test per scenario. Test name matches scenario name. 2. Real files, real I/O. No mocks for internal code. 3. Tests must fail before implementation exists. 4. Map tests: ptsd test map <bdd-file> <test-file> Profile gate: lite pipeline writes tests from PRD, not BDD.
write-prd write-seed write-bdd write-tests write-impl create-tasks workflow
review-prd review-seed review-bdd review-tests review-impl adopt

Quick Start

# Install
go install github.com/veschin/ptsd/cmd/ptsd@latest

# Initialize (auto-detects your AI tool)
cd my-project && git init
ptsd init

# Add features with the right pipeline
ptsd feature add auth "Authentication" --pipeline full
ptsd feature add config "App Config" --pipeline lite

# See what to do next
ptsd context --agent
# next: auth   stage=prd action=write-seed   pipeline=full
# next: config stage=prd action=write-tests  pipeline=lite
