PTSD

A structured development pipeline for AI-driven projects.

AI agents produce code. PTSD ensures the code was worth producing.

go install github.com/veschin/ptsd/cmd/ptsd@latest

Go 1.25+ / single binary / zero dependencies / 23 commands

Most AI-generated code is written before the problem is understood.

Requirements are vague, tests are afterthoughts, edge cases are discovered in production. The default mode of every AI coding agent is to produce -- quickly, confidently, and without proof that the output is correct.

PTSD is a CLI tool that enforces a different order of operations. Before code exists, requirements must be defined. Before implementation begins, tests must be written. Before tests are written, the expected behavior must be specified. Each stage produces a concrete artifact. Each artifact is reviewed and scored. Nothing proceeds without evidence.

The pipeline does not rely on the AI choosing to follow instructions. Hook scripts intercept every file write during a session. Write a test before the BDD scenarios exist -- blocked. Write implementation before tests exist -- blocked. Commit with a broken pipeline -- blocked.

The AI follows the pipeline because it cannot do otherwise.

The Pipeline

Five stages. Each produces a concrete artifact. Each feeds the next. Nothing proceeds without review.

01

PRD -- Requirements

A section in .ptsd/docs/PRD.md anchored to the feature. Defines what is being built, acceptance criteria as testable statements, edge cases, and explicit non-goals. The AI reads this as a binding constraint.

<!-- feature:auth -->
## Authentication

Users log in with email and password.

Acceptance criteria:
- Valid credentials return a JWT token
- Invalid credentials return 401
- Locked accounts return 403 with reason

Non-goals: social login, 2FA
02

Seed -- Test Fixtures

Real data in .ptsd/seeds/<feature>/. Not test_user or foo@bar.com -- actual records representing happy paths, edge cases, and invalid states. Seed data grounds BDD scenarios and tests in reality rather than abstractions.

v2: required only in the full pipeline profile. Standard and lite profiles skip this stage.

# .ptsd/seeds/auth/users.json
[
  {"email": "ada@example.com", "role": "admin", "status": "active"},
  {"email": "locked@test.co", "status": "locked", "reason": "brute force"}
]
03

BDD -- Behavior Specification

Gherkin scenarios in .ptsd/bdd/<feature>.feature. Each scenario is a testable claim: given specific preconditions, when an action occurs, a specific outcome follows. Scenarios map 1:1 to acceptance criteria from the PRD.

v2: required in full and standard profiles. Lite profile writes tests directly from PRD.

@feature:auth
Feature: Authentication

  Scenario: Successful login
    Given user "ada@example.com" exists and is active
    When valid credentials are submitted
    Then a JWT token is returned

  Scenario: Locked account
    Given user "locked@test.co" has status "locked"
    When login is attempted
    Then 403 is returned with reason "brute force"
04

Tests -- Proof Before Code

Test files that fail. Written before any implementation exists. One test per BDD scenario. Real file I/O, real assertions, no mocks for internal code. Tests define what "done" means. Mapped to features via ptsd test map.

// auth_test.go -- written before implementation exists

func TestLogin_ValidCredentials(t *testing.T) {
    user := seedUser(t, "ada@example.com", "active")

    token, err := auth.Login(user.Email, user.Password)

    assert(t, err == nil)
    assert(t, token != "")
}

func TestLogin_LockedAccount(t *testing.T) {
    user := seedUser(t, "locked@test.co", "locked")

    _, err := auth.Login(user.Email, user.Password)

    assert(t, errors.Is(err, auth.ErrLocked))
}
05

Implementation

Code that makes failing tests pass. Nothing speculative, nothing extra. The previous four stages already established what to build, what data it handles, what behavior to expect, and how to verify correctness. Implementation is the smallest part of the pipeline.

// auth.go -- only what makes tests green

func Login(email, password string) (string, error) {
    user, err := store.FindByEmail(email)
    if err != nil {
        return "", ErrInvalidCredentials
    }
    if user.Status == "locked" {
        return "", ErrLocked
    }
    if !verify(password, user.HashedPassword) {
        return "", ErrInvalidCredentials
    }
    return generateJWT(user), nil
}

Pipeline Profiles

Not every feature requires the full ceremony. A configuration utility does not need seed data. A simple helper does not need BDD scenarios. Pipeline profiles allow each feature to follow the stages it actually needs.

full
PRD Seed BDD Tests Impl
Data-heavy features. Seed data grounds BDD scenarios in reality.
standard
PRD Seed BDD Tests Impl
Default. BDD scenarios written directly from PRD. No seed ceremony.
lite
PRD Seed BDD Tests Impl
Simple features. Tests written directly from PRD acceptance criteria. 
ptsd feature add auth "Authentication" --pipeline full
ptsd feature add config "App Config" --pipeline lite
ptsd feature pipeline auth standard   # change later if needed

Enforcement

The pipeline is not advisory. Four hooks intercept the AI session at every decision point.

Session Start

Pipeline state is injected. The AI sees every feature, its current stage, and the next required action.

$ ptsd context --agent
next: auth   stage=prd   action=write-seed  pipeline=full
next: config stage=prd   action=write-tests pipeline=lite

Before Every Write

A gate check runs before each file edit. If the file belongs to a stage the feature has not reached, the write is rejected.

$ ptsd gate-check --file src/auth.go --agent
err:pipeline no tests for auth

After Every Write

When an artifact is created (a BDD file, a test file), the feature stage advances automatically. No manual tracking.

$ ptsd auto-track --agent
tracked: auth stage=bdd tests=written

On Commit

A pre-commit hook runs ptsd validate. Every active feature is checked. Scope must match staged files. Pipeline violations block the commit.

$ git commit -m "[IMPL] feat: auth"
err:pipeline auth: review gate not passed for stage tests

Review gate: each stage requires a score of 7/10 or higher before advancing. Scores below threshold auto-create redo tasks.

Skills

13 specialized instruction sets, one for each pipeline action. The AI does not improvise how to write BDD scenarios or review a PRD -- it follows a concrete checklist with known failure modes. Skills are loaded automatically by the AI tool during the relevant stage.

write-prd
## Instructions

1. Start with a one-line summary of the feature purpose.
2. Define the problem being solved and who it affects.
3. List acceptance criteria as testable statements.
4. Define non-goals explicitly.
5. Cover edge cases: empty input, missing files, invalid state.
6. Add a feature anchor: <!-- feature:<id> -->

## Common Mistakes

- Acceptance criteria that cannot be tested
- Missing non-goals (causes scope creep)
- Vague language: "handle errors" instead of specifics
write-tests
## Instructions

1. One test per BDD scenario. Names match scenarios.
2. Real files, real I/O. No mocks for internal code.
3. Tests must fail before implementation exists.
4. Map: ptsd test map <bdd-file> <test-file>

## Profile gate
Lite pipeline: tests from PRD, not BDD.
Map: ptsd test map --feature <id> <test-file>

## Common Mistakes

- Only checking err == nil without verifying values
- Tests that pass in sequence but fail individually
review-impl
## Review Checklist (score 0-10)

- [ ] All tests pass
- [ ] No code beyond what tests require
- [ ] Error format follows project convention
- [ ] No mocks for internal code
- [ ] Package/module boundaries respected
- [ ] No dead code or speculative features

## Common Mistakes

- Accepting code that works but is not tested
- Not verifying error format consistency
- Missing edge case handling from PRD

Integration

ptsd init detects the AI tool in use and generates the appropriate configuration. Enforcement depth depends on what the tool supports.

Tool Generated files Enforcement
Claude Code .claude/settings.json hooks, .claude/skills/, CLAUDE.md Full. Every write gated, every stage tracked, context at session start.
OpenCode .opencode/plugins/ptsd.ts, .opencode/commands/, AGENTS.md Full via plugin. Same hooks, different runtime.
Generic AGENTS.md, .git/hooks/ Advisory. Git hooks enforce at commit. No real-time gating. 
ptsd init --tool claude      # explicit selection
ptsd init                    # auto-detects from .claude/ or .opencode/
ptsd init --tool opencode   # switch existing project to opencode

Git hooks (pre-commit, commit-msg) are generated for all tools. They validate pipeline state and commit message format regardless of the AI tool in use.

Getting Started

# Install
go install github.com/veschin/ptsd/cmd/ptsd@latest

# Initialize a new project
cd my-project && git init
ptsd init

# Add features with appropriate profiles
ptsd feature add auth "User Authentication" --pipeline full
ptsd feature add config "App Configuration" --pipeline lite
ptsd feature status auth in-progress

# The AI sees what to do
ptsd context --agent
# next: auth   stage=prd action=write-seed  pipeline=full
# next: config stage=prd action=write-tests pipeline=lite

# Work through the pipeline. Review each stage.
ptsd review auth prd 8
ptsd validate --agent

# Adopt an existing project
ptsd adopt --dry-run    # preview discovered features
ptsd adopt              # creates .ptsd/ structure
ptsd migrate            # upgrade v1 projects to v2
